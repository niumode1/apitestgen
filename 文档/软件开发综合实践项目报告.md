## 1. 项目背景与意义

### 1.1 问题陈述

在传统软件开发流程中，接口测试用例的编写是一项高度重复、耗时且依赖人工经验的工作。测试工程师需要：

- 阅读接口文档，理解参数语义和约束
- 手动编写大量 pytest/JUnit 测试代码
- 覆盖正向、负向、边界值、安全等多种场景
- 逐一验证响应结构和状态码

一个中型微服务项目（30+ 接口）通常需要 **3-5 人天**来完成基础测试用例编写，且容易遗漏边界场景。

### 1.2 解决方案

本平台利用**大语言模型（LLM）** 的代码生成能力，自动完成从 OpenAPI 文档解析到 pytest 测试代码生成、执行、报告输出的全流程。核心思路：

```
OpenAPI 文档 → LLM 分析接口语义 → 并行生成多类测试 → AST 校验 → 执行 → 报告
```

### 1.3 项目目标

| 目标 | 指标 |
|------|------|
| 自动化测试生成 | 单个接口 5 种策略全覆盖，30 接口 < 3 分钟 |
| 可执行性 | 生成代码通过 AST 校验，pytest 可直接运行 |
| 报告可视化 | Markdown 格式，按类别统计通过率 |
| 多 LLM 支持 | OpenAI / DeepSeek / Anthropic / 本地模型 |

## 3. 系统架构设计

### 3.1 整体架构

系统采用**前后端分离 + 异步服务层**架构，分为四层：

> 📊 **[图3-1] 系统架构图**
>
> 见 `architecture.svg` — 展示了前端(Vue 3)、后端API(FastAPI)、服务层(SpecParser/LLM Engine/Executor/ReportGen)、数据层(SQLite)以及外部LLM的完整层次关系。

**架构说明**：
- **前端层**：Vue 3 + Element Plus，提供工作区管理、测试生成配置、执行结果展示
- **API 层**：FastAPI 异步路由，10 组 REST 端点 + WebSocket 推送
- **服务层**：核心业务逻辑，包含 OpenAPI 解析器、LLM Agent 引擎、pytest 执行器、报告生成器
- **数据层**：SQLAlchemy ORM + SQLite（可切换 PostgreSQL）

### 3.2 核心流水线

> 📊 **[图3-2] 核心流水线图**
>
> 见 `pipeline.svg` — 展示了从"上传OpenAPI文档"到"查看缺陷报告"的完整处理流程。关键环节：
> - 分析阶段：AnalyzerAgent 提取参数语义
> - 并行生成阶段：5个专项Agent同时生成不同类型的测试
> - 校验阶段：CodeGen 通过 AST 解析确保代码语法正确
> - 执行阶段：pytest 子进程运行，JSON Report 解析入库

### 3.3 技术选型

| 层级 | 技术 | 选型理由 |
|------|------|------|
| 前端框架 | Vue 3 + TypeScript | 响应式数据绑定，Element Plus 成熟组件库 |
| 构建工具 | Vite 8 | 毫秒级 HMR，开发体验极佳 |
| 后端框架 | FastAPI (async) | 原生异步支持，自动生成 OpenAPI 文档 |
| ORM | SQLAlchemy 2.0 async | 异步查询，支持 SQLite/PostgreSQL 切换 |
| LLM SDK | OpenAI SDK | 同时兼容 DeepSeek/Ollama/vLLM |
| 测试框架 | Pytest + httpx | Python 生态标准 |
| 模板引擎 | Jinja2 | Prompt 模板和报告渲染 |

## 4. 数据库设计

### 4.1 ER 图

> 📊 **[图4-1] 数据库 ER 图**
>
> 见 `er_diagram.svg` — 9 张核心表的完整实体关系图。

### 4.2 核心表说明

**projects（项目表）**：顶层容器，关联所有 API 文档和测试资产。`base_url` 字段指定目标 API 地址。

**specs（OpenAPI 文档表）**：存储原始文档内容和解析结果，`raw_content` 保留原文，`parsed_json` 存储规范化 JSON。

**endpoints（接口表）**：一行对应一个 API 接口（path + method），`parameters`、`request_body`、`responses` 以 JSON 存储完整 Schema。

**testcases（测试用例表）**：LLM 生成的 pytest 代码，`test_code` 存储完整函数体，`category` 标记用例类型（positive/negative/boundary/security/schema），`status` 支持审阅流程（draft→reviewed→approved→disabled）。

**executions + test_results（执行 + 结果表）**：一次执行可包含多条结果，每条结果关联到具体用例。

**defect_reports（缺陷报告表）**：基于执行结果生成，存储 Markdown 内容和文件路径。

**llm_providers（LLM 提供商表）**：API Key 加密存储，支持 openai/anthropic/openai_compatible 三种类型。

## 5. 核心功能实现

### 5.1 OpenAPI 文档导入

**实现文件**：`backend/app/api/v1/specs.py`、`backend/app/services/spec_parser.py`

**关键逻辑**：

```python

if filename.endswith(".yaml"):
    parsed = yaml.safe_load(raw_content)
else:
    parsed = json.loads(raw_content)

# 2. 验证 OpenAPI 3.x
if "openapi" not in parsed:
    raise HTTPException(400, "Not a valid OpenAPI 3.x spec")

# 3. 遍历 paths 提取端点
for path, path_item in parsed.get("paths", {}).items():
    for method in ["get","post","put","delete","patch"]:
        operation = path_item.get(method)
        if operation:
            # 创建 APIEndpoint 记录
```

**支持的导入方式**：
- 文件上传（multipart/form-data）
- URL 导入（POST /specs/import-url）

### 5.2 测试用例生成

**实现文件**：`backend/app/services/llm/agents/orchestrator.py`

**核心流程**：

1. 加载 Spec + Project，获取 Base URL
2. 生成 `conftest.py`（async_client fixture）
3. 遍历 Endpoint，每批 Semaphore=3 并发处理
4. 每个 Endpoint 内部：AnalyzerAgent → 选择策略 → Agent 并行生成 → CodeGen 校验 → 入库

**关键代码**：

```python
# 并行生成多种测试
agent_tasks = []
if strategy in ("all", "positive_only"):
    agent_tasks.append(("positive", PositiveCaseAgent(provider).generate(...)))
if strategy in ("all", "negative_only"):
    agent_tasks.append(("negative", NegativeCaseAgent(provider).generate(...)))
# ... 5种Agent

results = await asyncio.gather(*[task for _, task in agent_tasks])

for idx, (cat_name, _) in enumerate(agent_tasks):
    code, pt, ct = results[idx]
    parsed = parse_llm_output(code)  # AST 校验
    await _save_testcases(endpoint, parsed, category, ...)
```

### 5.3 测试执行引擎

**实现文件**：`backend/app/services/executor_service.py`

使用 `subprocess.run` 在独立进程中执行 pytest，通过 `pytest-json-report` 插件获取结构化结果：

## 6. LLM Agent 体系

### 6.1 Agent 架构

> 📊 **[图6-1] LLM Agent 体系图**
>
> 见 `agent_architecture.svg` — 展示了 Provider 抽象层 → BaseAgent 基类 → 6个专项Agent → Orchestrator 编排器 → CodeGen 代码生成的完整 Agent 体系。

### 6.2 Agent 职责

| Agent | Prompt 模板 | 生成内容 |
|------|------|------|
| **EndpointAnalyzerAgent** | `analyzer.j2` | 参数语义、约束、测试建议（JSON） |
| **PositiveCaseAgent** | `positive.j2` | 合法参数 → 期望 200/201 |
| **NegativeCaseAgent** | `negative.j2` | 缺参数/错类型/非法值 → 期望 400/422 |
| **BoundaryValueAgent** | `boundary.j2` | min/max±1/零值/空值/超长 |
| **SecurityPayloadAgent** | `security.j2` | SQL注入/XSS/路径穿越 |
| **SchemaValidationAgent** | `schema_v.j2` | 响应字段类型/必填校验 |

### 6.3 Provider 抽象

```python
class BaseLLMProvider(ABC):
    @abstractmethod
    async def complete(self, system_prompt, user_prompt, temperature, max_tokens) -> LLMResponse

class OpenAIProvider(BaseLLMProvider):     # OpenAI + 所有兼容API
class AnthropicProvider(BaseLLMProvider):  # Claude
class LLMProviderFactory:                  # 工厂模式自动选择
```

同一套 Agent 代码通过 Provider 切换即可对接不同 LLM。

### 6.4 Prompt 质量控制

- 所有 Prompt 使用 Jinja2 模板管理，与代码分离
- CRITICAL RULES 区块针对性修复了 LLM 常见错误（假通过、硬编码ID、字段名猜测）
- Example 格式引导 LLM 生成规范的 pytest 代码

### 8.2 端到端测试

```
导入 OpenAPI → 生成 30 条测试 → 执行 → 15/15 通过 (50%) → 缺陷报告
```

## 9. 项目总结与展望

### 9.1 成果总结

| 维度 | 成果 |
|------|------|
| **自动化程度** | 导入文档 → 一键生成 → 一键执行 → 自动报告 |
| **测试覆盖** | 5 种策略，每接口 3-14 条用例 |
| **生成速度** | 19 接口全策略 < 120s（并行 Semaphore=3） |
| **代码质量** | AST 语法校验 + Prompt 质量规则 |
| **多 LLM 支持** | OpenAI / DeepSeek / Anthropic / Ollama |
| **代码规模** | 后端 ~3500 行 Python，前端 ~2500 行 Vue/TS |

### 9.2 技术创新点

1. **Agent-per-Category 架构**：每个测试类别独立 Agent，通过 Jinja2 模板控制生成质量
2. **并行编排**：asyncio.Semaphore 控制并发，5 个 Agent 同时生成
3. **AST 双保险**：LLM 输出 → 正则提取代码块 → `ast.parse()` 语法校验 → 才入库
4. **Provider 工厂模式**：一套 Agent 代码适配所有 LLM 后端

### 9.3 不足与改进

| 问题 | 改进方向 |
|------|------|
| LLM 生成的断言不精确 | 引入 Schema 感知的响应校验 |
| 执行耗时显示不稳定 | 改用 pytest JSON report 顶层 duration |
| 大规模项目慢 | 支持增量生成（仅变更接口） |
| 缺少 CI/CD 集成 | GitHub Actions / Jenkins 插件 |
| 缺少用户系统 | 多用户 + 权限管理 |

### 9.4 未来方向

- **定时任务**：定时监控 API 健康
- **智能修正**：LLM 分析失败原因，自动修复测试
- **性能测试**：集成 Locust/k6
- **Mock 服务**：根据 OpenAPI 自动生成 Mock Server
- **PDF 报告**：WeasyPrint 生成正式报告
